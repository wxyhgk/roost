# 终端停帧：前端回归排查

## 范围

用户反馈运行一段时间后画面停住，刷新页面恢复，要求优先检查近期前端修改。本轮不修改后端，不重启用户终端。

## 已确认并修复：控制器拆分丢失相同状态去重

HEAD 中 `useTerminal.ts` 使用独立 `useState(true)` 保存 `atBottom`。xterm 的 `onScroll` 和 `onWriteParsed` 都通知该值，React 会跳过相同布尔值。

当前拆分后的 `sessionController.ts` 将状态合并为对象，`update({atBottom})` 每次都创建对象并通知 React。持续输出时，即使始终在底部也会不断提交状态。React 可能合批这些提交，通知次数不等于实际 DOM 重绘次数，但相比旧实现已确定增加无效工作。

修复：仅在 patch 中至少一个字段发生变化时创建新状态并通知视图。真实状态变化仍立即发布；没有添加定时刷新或自动重建。

回归测试先在旧实现失败：10,000 次相同底部通知，状态提交数由 2 增至 10,002。修复后相同通知不再提交，离开/回到底部以及连接状态变化仍正常发布。

## 真实 xterm 隔离压测

入口：`frontend/tests/browser/terminal-output-lifecycle.html`。使用当前 `mountXterm` 与 `createResume`，无 PTY、WebSocket 或业务后端。包含长行、中文、emoji、同步输出控制序列、持续输出、容器缩放、CSS 隐藏/显示。CSS 隐藏不等于浏览器后台计时器节流，未覆盖操作系统休眠。

一次浏览器实测：

- 24,001 帧，约 12.2 秒完成，已接收与已解析序号均为 24,001。
- 队列与 pendingWrites 归零，末尾标记存在。
- 85,609 次滚动/解析通知，底部值仅初次报告一次，之后未变。
- WebGL 上下文丢失为 0，浏览器错误为 0，未出现永久停帧。

这些结果证明状态通知路径存在明显冗余；没有证明它是用户永久卡屏的唯一根因，也不构成长时间稳定性验收。

## 仍待现场证据的问题

`resume.ts` 等待 xterm 写入回调后才推进游标。如果解析内部异常导致回调丢失，输出和 prepare 会一起阻塞；该串行等待机制在 HEAD 已存在。当前不能通过这一条件推导用户实际发生了解析异常，也不能靠跳过回调来修复，否则会错误确认未解析输出。

若再次停帧，需要对照已有诊断中的接收/解析序号、pendingWrites、队列、显示尺寸与 WebGL 上下文丢失次数，并保留当时浏览器异常。没有这些证据，不贸然升级 xterm、回退所有重构或添加自动刷新。
