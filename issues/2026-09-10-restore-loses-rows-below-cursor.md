# 恢复画面后，光标下面的几行被吃掉；TUI 不会重画

**状态**：已修复。**但第一次判断只对了三分之一**——见第零节。
**影响**：刷新页面后，AI CLI（omp 实测）底部的输入框只剩上边框，下边框和状态行消失。
必须手动拖动侧边栏比例、或点「恢复画面」/「重新加载视图」才恢复。

标注 **[实测]** 的是本次跑出来的数字，其余为推断。

---

## 零、先读这一节：结论修正过两次

这份文档最初的结论是「字体 swap 导致缩行」，并按那个结论做了修复。**修完之后 bug 又出现了。**
完整的成因有三条，字体只是其中一条：

| # | 成因 | 修法 | 提交 |
|---|---|---|---|
| 1 | **量的时候字体还没到**（`display=swap` 换字体，格子高度变了） | 量之前先等字体 | `7a43a69` |
| 2 | **坏掉的一屏被永久复用**——快照存在 sessionStorage 里跨刷新存活，而增量里没有任何字节能纠正它 | 快照只在本次页面加载内有效；服务端网格 500→2000 行 | `63bddf8` |
| 3 | **本地缩了行而 PTY 没被告知新尺寸**——挂载路径绕过了「尺寸必须一起改」那道门 | 检测到这个组合就丢掉本地这一屏、向服务端重取 | `3dd721d` |
| 4 | **我们自己的写入被当成了用户的滚动**——恢复要灌几百行，灌的过程中视口落后，`atBottom` 变假，于是恢复结束时那次「回到底部」被跳过，此后再没人拉回来 | 把「用户想不想跟着底部」和「此刻在不在底部」分开：恢复期间不更新意图 | 见下 |

**三条的共同底层机制是同一个**（第三节讲的那个），字体只是触发它的一种方式；而第 2 条决定了
「触发一次 = 永远坏着」，这正是修完第 1 条之后 bug 看起来「复发」的原因——它从来没被治好，
是那份坏快照一直在被恢复。

判断第 2 条的决定性证据只用了 30 秒：**换个无痕窗口一切正常。**
下次遇到同类问题，先做这个检验，再谈机制。

第 4 条是诊断面板直接读出来的（`视口位置: 停在上方 25 行 (470/495)`，而`容器可容纳/实际`
是 49/49、输出游标 474/474）——**几何正常、数据齐全、视口不在底部**，一眼就和前三条分开。
面板上那两行就是为分开这三种成因加的，这次它第一次派上用场。

## 一、现象

刷新页面后进入终端，omp 的 composer 只画出上边框，光标停在下一行，**再往下什么都没有**。

三种操作能恢复：拖动左右侧边栏比例、点「恢复画面」、点「重新加载视图」。
**光是滚动不行**——[实测] 往上滚一行再滚回底部，缺的行不会出现。

出现是间歇的，不是每次。

---

## 二、证据

### 诊断面板（坏状态下）

```
renderer: WebGL, contextLosses: 0
width 1066, height 842, cols 140, rows 49, cellHeight 17
frozen false
viewportY 500 = baseY 500        → 视口在底部
fitsRows 49  = rows 49           → 49×17=833 装在 842 里，没被容器裁
replay: applied 201 = received 201, queued 0, behind 0
events: waiting-for-layout → renderer-mounted → socket-connect → hello → catchup(200) → replay-applied
```

几何、滚动位置、数据链路**全部正常**。`applied = received` 说明服务端发的每个字节都到了、都应用了，
所以缺的行不是丢在传输上——**它们从来没被写进缓冲**。

### PTY 真实尺寸（`stty -f /dev/ttysNNN size`，每秒一次，采样 9 分钟）

```
19:47:39  ttys002  24x80  -> 49x140     点进一个从未打开过的终端
19:51:27  ttys008  49x140 -> 49x134     往左拖侧边栏
19:51:50  ttys008  49x134 -> 49x140     拖回来
19:52:13  ttys006  49x140 -> 49x134
```

**[实测] 行数从头到尾都是 49，一次都没变过。** 出问题那一刻 PTY 就是 49×140；
拖动只是把它变成 134 再变回 140 —— **恢复靠的是那一次 SIGWINCH，不是把错的尺寸改对了。**

### 缩行会吃掉光标下面的行（headless 复现）

用 `@xterm/headless` 造一个底部有 composer 的画面，把光标放在输入行，然后 resize：

```
不 resize        ✅ 没丢
行数 49 → 48     ❌ 丢了 1 行: ["pi · Muse Spark · ctx: 76.6%"]   ← 光标下面那行
列数 140 → 139   ✅ 没丢
```

**只有缩行会丢，丢的正是光标下面的行**——和截图里「虚线、光标、然后什么都没有」一致。

### 序列化往返本身是无损的

同样用 headless 测 `@xterm/addon-serialize` 的 serialize → 写回，65 行**逐行相同**。
所以问题不在序列化，在序列化**之后**发生的那次 resize。

## 三、机制

`frontend/index.html:14` 从 Google Fonts 加载终端字体，带 `display=swap`——
**先用回退字体渲染，字体到了再换掉**。而 `frontend/src/terminal/index.ts:7` 的 `waitForSize`
只等容器有尺寸，**不等字体**。

于是：

1. 挂载时字体未到 → xterm 按回退字体（macOS 上是 SF Mono）量格子 → 行数偏大
2. `resume.prepare()` 把 sessionStorage 里的快照写回去，**光标落在 composer 的输入行**
3. IBM Plex Mono 到达 → swap → 格子高度变成 17px
4. `replay-applied` 之后的那次 `fit()` 重算 → `842/17 = 49` 行 → **缩行**
5. xterm 重排，**吃掉光标下面的行** —— 正好是 composer 的下边框和状态行
6. 这次 `fit()` 告诉 PTY 的是 140×49，而 **PTY 本来就是 140×49** → 相同 winsize
   内核不发 SIGWINCH（这一点本仓早前已实测确认）→ omp 永远不知道要重画

`842/16 = 52` vs `842/17 = 49`，缩 3 行，和截图里缺的行数吻合——但回退字体的实际行高**没有实测**，
这一步是算术推断。机制本身（缩行吃掉光标下面的行）是实测的。

### 每条现象都对得上

| 现象 | 解释 |
|---|---|
| 光标下面全没了 | 缩行重排的指纹 |
| PTY 日志里行数从没变过 | 那次 fit 发的尺寸和 PTY 已有的相同 |
| 只有拖边框 / 恢复画面 / 重载能修 | 三者都产生**不同**的尺寸 → 真的 SIGWINCH |
| `fitsRows == rows` | 缩完之后自洽，看不出曾经更大 |
| 滚动修不好 | 内容根本不在缓冲里，重画无从画起 |
| 只是有时候出现 | 字体在 HTTP 缓存里就不触发；冷缓存 / 慢网才会 |

### 更深一层：它违反的是已经写下来的那条不变式

`sessionController.ts` 的 `fit()` 上方有一大段注释，讲的正是「本地终端和 PTY 的尺寸必须一起改」。
但**挂载路径绕过了这道门**：`mountEngine` 内部直接 `fitExact(term)`，本地单独定了尺寸，PTY 不知道。
等到 `inputReady` 之后第一次 `conn.fit()`，发过去的尺寸恰好等于 PTY 已有的，于是
「本地缩过一次而 PTY 从未见过那个中间尺寸」这件事被永久吞掉。

## 四、修复

> 本节写于只发现第 1 条成因时。**它是对的，但不完整**——第 2、3 条见第零节的表格。

### 1. 量之前先等字体（成因之一，不是全部）

新增 `frontend/src/terminal/font.ts`：

```ts
export async function waitForMeasurable(el, signal?) {
  await waitForBox(el, signal);   // 容器有尺寸
  await waitForFont(signal);      // 字体已经定下来 ← 新增
}
```

`waitForFont` 等 `document.fonts.load('13px "IBM Plex Mono"')` 和 `fonts.ready`，
**带 2 秒超时**——字体 CDN 挂掉只该让字变丑，不该让终端起不来。

原来的 `waitForSize` 改名为 `waitForMeasurable`：它等的不只是尺寸了，旧名字会骗人。
字体常量从 `xtermEngine.ts` 挪进 `font.ts` 并导出——「等的是谁」和「用的是谁」写死在两处迟早分叉。

**单独一个模块，是因为它不能把 xterm 拖进来**：这条规则值得有测试，而测试不该为了几十行去加载渲染器。

### 2. 字体晚于超时到达的兜底

`observeFonts()` 订阅 `document.fonts` 的 `loadingdone`，控制器拿它当第二个重测触发源
（`sessionController` 的 `deps.observeFonts`）。容器一个像素都没变，`ResizeObserver` 不会响，
只有这条路能发现。

**这一路是安全的**：那时候本地缩行的同时 **PTY 的尺寸也真的变了**（PTY 之前被告知的是偏大的行数），
SIGWINCH 会发出去，TUI 自己会重画。危险的只有「本地变了而 PTY 没变」那一种，
也就是挂载那次——第 1 条正是消除它。

### 3. 明确没有做：用「抖一下尺寸」强制重画

那等于人为制造 SIGWINCH，而 omp 收到 SIGWINCH 会把整段对话重新打印一遍
（见 `tasks/terminal-flood/README.md`）。修因，不要修果。

### 4. 诊断面板补了两行

`视口位置`（`viewportY` vs `baseY`）和 `容器可容纳 / 实际`（`fitsRows` vs `rows`）。
少了这两个数，「内容在缓冲里但没显示」的三种成因——滚动位置、容器裁切、渲染器陈旧——
在面板上长得一模一样。这次排查有一半时间花在把它们分开上。

### 验证

`frontend/tests/terminal-font.test.ts` 5 条。
**[实测] 去掉 `await waitForFont(signal)` 那一行会红 3 条。**
