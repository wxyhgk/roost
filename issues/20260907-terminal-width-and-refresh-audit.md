# 终端内容只占左半边：布局、刷新与共享 PTY 尺寸调查

日期：2026-09-07。状态：四个 subagent 只读调查完成，尺寸仲裁尚未修复。

## 用户提供的关键证据

截图 `c616554c712edfdc382f8b400eff06e764af739f51e50b423f56f68e139392e1.png` 中，终端仍显示输出和输入框，但 CLI 横线仅占中间面板左侧约一半。不能把这种现象与整个终端被隐藏混为一谈。

最符合截图的候选机制是本地画布较宽，而共享 PTY 被另一个客户端改成较窄列数。没有当时的 resize 时序记录，仍不能认定该机制就是截图发生时的原因；也需排除 CLI 自身布局宽度限制。

## 已确认的代码路径

1. `frontend/src/terminal/connection.ts`：hello 后 ready 总携带本窗口 cols/rows，绕过显式 resize 的 canResize 门槛。
2. `backend/src/server.ts`：收到普通客户端 ready 就调整共享 PTY 尺寸，显式 resize 同样没有客户端所有权仲裁。
3. `frontend/src/terminal/sessionRuntime.ts` / `sessionController.ts`：5173 未启用稳定版的主动使用限制；可见且选中的终端即可 resize，没有窗口焦点要求。两个并排可见窗口均可能提交尺寸。
4. `packages/terminal-runtime/src/index.ts`：合法尺寸直接传给 PTY，最后提交者生效。本地 xterm 仍按自己的面板尺寸绘制。

这解释了“小窗口连接或重连后大窗口右侧空白，刷新大窗口暂时恢复”的可能链路。此前代理曾打开较窄的 Edge 测试页面，用户截图来自 Chrome；测试页面可能参与尺寸争抢，但没有足够现场证据确定归因。后续不得通过额外工作台标签页连接用户正在使用的 PTY 来验证。

## 排除与独立风险

- 5173 每 4 秒轮询只 patchLive cwd/cli；同值返回原 state，不删除会话或改选中项。TermView 按会话 ID 保持挂载，普通 render 不会重建终端。
- 调查时 8787 后端以 `tsx src/index.ts` 运行，非 watch，已运行约 6 小时；没有定时重启证据。
- Vite Fast Refresh 可重跑终端 effect，混合导出模块变更可能传播为整页 reload；Vite socket 断开恢复也可能 reload。这些是真实路径，但不是已确认的定时行为。
- 全量回放或连续输出累计 256 KiB 时，现有 freeze 使用 visibility:hidden，存在短暂整块空白；正常事件循环下有 1200ms 显示兜底，与截图半宽现象不同。
- hydrate 未校验 selectedId，稳定入口可能得到不存在的选中 ID，导致所有终端 invisible；全量请求缺少乱序保护。这些是独立风险，不能作为本截图根因。

## 本轮已经完成的布局调整

初始配置只有左栏 22%，其余空间由中间和右栏平分为 39%/39%。已明确设为 18%/64%/18%，中央最小 40%，两侧最小 12%、最大 30%。新增独立布局存储版本与设置中的“恢复默认布局”，使用 setLayout 调整，不以换 key 重建终端。

浏览器实测三栏约 278/989/278 px，多个轮询周期后保持稳定，活动终端可见。构建与边界检查通过。这不是尺寸所有权问题已修复的证明。

## 建议下一步

1. ready 不隐式改变共享 PTY 尺寸；实际交互窗口在握手完成后显式申请 resize。
2. 开发和稳定入口统一主动尺寸规则。跨网关权威仲裁宜放在 daemon，以连接/客户端租约明确所有权。
3. 记录尺寸请求来源、时间、旧新 cols/rows，用于区分画布、PTY 与 CLI 布局问题；不记录终端正文。
4. 用隔离 PTY 进行宽、窄双窗口测试：被动连接、重连、后台 resize 不改变主窗口尺寸；主动切换输入窗口才转移，PID 不变。
5. “冻结改为保留上一帧”和 hydrate 选中项校验分别处理，不与尺寸问题混在同一修复里。

已有回放、连接、控制器、诊断相关 28 项测试通过，但主要基于 mock，不能证明双客户端真实尺寸行为正确。
