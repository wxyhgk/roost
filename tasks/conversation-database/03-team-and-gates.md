# 多 Agent 分工与验收关卡

日期：2026-09-09。当前阶段：G1/G2 已完成本批代码与隔离自动化验收，未部署日常服务；G3 本轮真实 Claude 尝试已结束，关卡未放行。一次两跳传输与 HTTP/WS 断言通过不替代完整测试；后续模型拒绝协作，GUI 也尚待前端联调。最终记录见 [G3 实施](10-g3-implementation.md)、[测试](verification/g3-tests.md) 与 [反方](verification/g3-skeptic.md)。

用户要求本项目由多个 Agent 协作，必须包含独立测试人员和反方审查者。本文件将该要求作为本任务的实施约定，不能用“实现者跑了自己的测试”代替独立验收。

## 1. 角色与文件所有权

| 角色 | 核心职责 | 文件/模块所有权与交付 |
| --- | --- | --- |
| 主 Agent：集成负责人 | 收敛契约、拆分任务、解决跨模块争议、串行集成、汇总真实证据 | 本目录 README、分工与阶段状态；共享入口和导出统一集成，不与工作者同时编辑 |
| 数据库实现 Agent | catalog/sources/runs、信箱表、迁移、幂等事务、历史保留 | workspace-store 内明确分配的新模块；旧 schema/store/delete 路径按批次授予独占编辑权 |
| 投递实现 Agent | run 身份核验、收件箱调度、command 关联、回执与 uncertain 恢复 | terminal-daemon 内明确分配的投递模块；不得自行另开第二个原生执行器 |
| API/同步实现 Agent | 独立对话/收件箱 API、变化游标、断线补收、错误契约 | backend 新路由和同步模块；共享 server 入口由集成负责人接线 |
| 独立测试 Agent | 从产品要求写验收与故障用例，独立复现失败，执行迁移/并发/集成测试 | `04-test-plan.md`；实施阶段独占约定的验收测试文件和测试夹具，不直接修改业务实现 |
| 反方审查 Agent（“杠精”） | 主动找反例，挑战身份、事务、重试、删除、同步保证以及测试结论 | `05-skeptic-review.md`；实施阶段审查变更与证据，不自行悄悄修复后宣布通过 |

不是六个人立即同时改整个仓库。数据库基础先做；API 与投递在接口契约确定后才各自推进。测试设计、故障夹具和反方审查可与实现并行。

每次派工必须写清具体文件、允许修改的接口、依赖、验收条件，并告知“你不是唯一工作者，不要回退他人改动”。共享文件只允许一个当前所有者。实际所有权转交须记入阶段记录。

前端仍由用户安排的前端开发者负责。本团队准备接口和联调证据，不自行修改前端。浏览器可见效果最终需要前端人员或约定的联调测试人员验证，不能以后台 HTTP 成功替代。

## 2. 测试人员与杠精不是同一个职责

测试人员回答：“这些需求在正常与故障情况下，实际是否成立？”以可运行测试、观察值和复现步骤为依据。

反方回答：“即使现有测试全部通过，这个结论有没有不成立的情况？”可以指出测试过度 mock、故障注入位置错误、身份用错、不可观察的成功条件。必须给出触发条件、后果、依据和验证建议，不做无依据否定。

两者可互相挑战，但实现者不能单方面关闭自己的验收失败。主 Agent 负责判断事实、安排修复并保留结论，不把所有 subagent 的“完成”简单相加为项目完成。

## 3. 分阶段协作与关卡

编号对照：测试计划的 D0—D3 分别对应这里的 G0—G3；D4 表示其他 CLI 的扩展验收，需要对每个适配器重复 G3。本文件 G4 是最终交付检查，不等同测试计划的 D4。

### G0：设计可实施

- 数据模型明确 identity、删除策略、源命名空间、原生投递不确定状态。
- API 明确幂等键、sender 来源、目标选择、回执、序号与游标失效。
- 测试 Agent 交付独立故障矩阵；反方交付阻塞项和可验证反例。
- 阻塞实现正确性的设计争议需先由主 Agent 收敛，不能让不同工作者自行猜测不同契约。

G1/G2 范围内的契约已经收敛并实施；G3 仍需逐个 CLI 的原生接收证据与前端联调。文档存在不等于所有关卡已通过。

### G1：独立对话和迁移

- 数据库 Agent 实现目录、来源及历史保留；API Agent 在已固定契约上实现独立查询。
- 测试 Agent 从旧版 fixture 建库验证迁移；不得只用新 schema 创建空库后宣称兼容。
- 独立验证删除最后终端后历史仍可读、重复迁移不复制对话、旧接口可用、不同来源不误合并。
- 反方重点审查底层旧唯一约束、删除级联、迁移中断及旧进程仍运行时的兼容性。

### G2：通讯与恢复机制

- 数据库、投递、API Agent 按已有契约并行实现各自模块；共同修改的类型和事务边界串行接入。
- 测试 Agent 用隔离的多个数据库连接/进程与可控制的原生适配器，覆盖 A/B/C 并发、owner 竞争、断线补收和提交边界故障。
- 反方审查是否把数据库入库误认为原生执行成功，是否在 uncertain 后自动重发，是否存在旧 owner 继续写入。
- 测试适配器通过仅证明机制，不能开启未验证 CLI 的发送能力。

### G3：真实 CLI 与前端联调

- 选择一个具备可验证输入及回执能力的实际 CLI 版本。
- 在隔离环境证明 A 发 B、B 原生收到、B 显式回 A；记录相同原生 session/message ID，验证 TUI 与 GUI 对应同一执行。
- 独立测试确认草稿保护、忙时排队、退出恢复、不确定提交，以及刷新/重连后显示。
- 前端联调未完成、真实测试被跳过或 CLI 不支持时，清楚标记待验证；不能写成“端到端完成”。

### G4：交付

- 对最终集成版本执行适用的类型检查、相关测试与包边界检查。
- 测试报告列明实际运行命令、结果、失败/跳过项和环境；反方问题逐项有处理结论。
- 发布说明区分数据库能力、协议模拟验证、真实 CLI 版本支持与 GUI 可见行为。

## 4. 缺陷与反方问题的闭环

每条问题使用稳定编号，记录：严重性、场景、期望、实际/推断、证据、负责人、修正方案、复测结果、当前状态。

- **阻塞**：可能丢历史、误投对话、重复执行、不可靠迁移，或无法证明运行归属；相关阶段不能宣布通过。
- **重要**：状态/恢复/补收错误，或缺失关键故障测试；必须修复或明确缩小本批支持范围。
- **建议**：性能、可维护性或后续能力；可以排期，不因无限泛化妨碍本批交付。

开发者提交修复 -> 测试人员独立复测 -> 反方检查原反例是否消失 -> 主 Agent 更新结论。对没有证据的假设记录为待验证，不伪装成已复现缺陷。

## 5. 测试环境与证据

- 临时数据目录、独立 SQLite、独立 socket/端口与测试工作目录；不操作用户日常 daemon 或私人对话。
- 使用明确版本的旧库 fixture 和真实 CLI，记录相关代码版本/变更摘要；当前主工作区有多人未提交修改，HEAD 不足以代表所有测试输入。
- 类型检查、单元测试、跨进程故障测试、真实 CLI 测试和浏览器联调分开报告。跳过用例不能计入完成证据。
- G0 设计审查不运行真实模型或操作日常服务。用户随后授权实施的 G3 可以运行有界、隔离的真实模型通讯测试；这不授权重启日常服务或在私人会话中发送测试消息。

当前脚本入口已核对：`@roost/workspace-store`、`@roost/terminal-daemon` 和 `backend` 均有 test/typecheck，`@roost/ai-session-bridge` 有 test；边界检查为 `node scripts/check-boundaries.mjs`。具体命令与用例由测试负责人编排。G1/G2 已执行相关包全量回归；实际数量与跳过范围见各阶段 verification 报告。

## 6. 本轮实际人员安排

- 主 Agent：维护分工、共享入口集成、实际原生写入边界保护和最终交付。
- `database_test_review`：独立测试负责人，实施永久测试、故障夹具与全量回归，不修改业务实现。
- `database_skeptic_review`：G0/G1 反方审查者；G2 由 `qwen_adapter` 接任反方，独立复现和复测，不做 CLI 适配。
- `conversation_store_impl`：G1 数据库、迁移、历史保留与查询；G2 信封、收发件箱和回执实现。
- `conversation_api_impl`：G1/G2 HTTP、G2 WebSocket 与前端契约。
- `conversation_runs_impl`：G2 runs、投递协调器与 Agent 命令行。
- `conversation_changes_impl`：G2 持久变化日志、触发器与游标。

以上角色已按批次实际参与并留下代码、独立测试和反方验证记录。G2 独立 QA 另获授权修正既有 owner 测试的固定等待为有界轮询，保留原 PID/instance/replay 断言；这是测试稳定性修正，失败过程保留在报告。

G3 继续由 `database_test_review` 独立实现与执行真实夹具、`qwen_adapter` 担任反方；`conversation_runs_impl` 核验本机 CLI 前置条件，`conversation_api_impl` 准备前端交接，主 Agent 负责隔离启动条件、共享检查与阶段收口。来信不构成独立任务授权：实际收件模型拒绝时记录拒绝，最终验证改为用户先在 B 原生会话明确下达协作任务，不能用控制器代发回信获得通过。
