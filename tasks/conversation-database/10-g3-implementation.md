# G3：真实 CLI 通讯验收

日期：2026-09-09。状态：本批隔离真实验证已结束，**G3 未放行**。第七次曾完成真实两跳和 HTTP/WS 断言，但整项测试失败；第八、九次模型拒绝协作，未形成稳定闭环。最终结果见 [独立测试报告](verification/g3-tests.md) 和 [反方复核](verification/g3-skeptic.md)。本批先推进后端；前端由前端负责人接入，不以 HTTP 成功替代浏览器验收。

## 1. 本批目标

选择本机 Claude Code 2.1.266，版本与现有 command writer 门禁一致。用临时工作目录内的真实交互终端完成 A → B → A：A 的模型实际调用工具发信，B 在自己的原生会话内接收后显式回信，A 在原会话内继续回答。另开空闲 C 验证非目标不受影响，C 不提交模型任务。

仅运行有界的合成通讯任务，不使用日常终端或私人对话，不更改日常发送开关。每次测试拥有独立 workspace 数据目录、socket、HTTP 端口、原生会话和清理责任。配置、认证及权限前置条件须在实际报告中记录；缺失时明确失败或未执行，不替换成 fake CLI 宣布通过。

## 3. 不能省略的证据

1. **来源真实**：使用 launch hook 自动建立 binding；测试不能直接 `bridge.bind()` 或假造已识别 CLI。记录 A/B 各自原生 session、稳定 conversation 与 run 的对应关系。
2. **模型实际发信**：A/B 的原生 transcript 各有真实工具调用和成功工具结果。脚本是工具的一部分；测试控制器直接调用 send 不能替代模型调用证据。
3. **送达有回执**：两封信的 sender、recipient、reply 关系正确；acceptedNativeMessageId 对应目标原生 transcript 中真实 user 记录，正文与 command 的可信来源前缀一致。
4. **回答不能取巧**：最终标记必须来自 assistant 的文本段，不能扫描整个 JSON 后误中 seed、工具参数或终端回显。
5. **同一个执行实例**：记录 PTY PID/instance 和 native ID，投递不另开 CLI 执行器。TUI 的输出应可由真实终端流解析，HTTP 历史具有同一消息 ID。
6. **补收有效**：快照和 WS 断开再连接期间发生的变更能按 cursor 补收，HTTP 历史/信箱可以重新获取；重启 gateway 后按契约重新快照。
7. **保护仍有效**：既有草稿、忙、权限与 uncertain 的公共回归继续执行。G3 未实际覆盖的故障场景单独列出，不用 G2 fake writer 结果冒充真实 CLI 故障验收。

## 4. 联调边界

本批测试可以证明原生 transcript、真实终端输出与网页所读 API 一致；GUI 的布局、去重渲染、草稿保留及浏览器刷新仍需前端联调。见 [前端交接](11-g3-frontend-handoff.md)。

真实验证限定明确的 CLI 版本及配置，不能推导所有 Claude 版本或 Qwen/OpenCode/Codex 都支持同一输入方式。未经过真实接收回执验证的适配器继续保持自己的能力门禁。

## 5. 启动前置核验

本机实际 `claude --help` 的权限模式已使用 `manual` / `dontAsk` 等值，没有旧测试中的 `default`。本批采用 `dontAsk` 配合精确允许的测试脚本；不使用 bypassPermissions。严格禁用外部 MCP，保留当前 launch observer 插件，不能用会关闭 hooks 的 bare/safe 模式替代真实接线。

既有 `backend/tests/claude-send-live.test.ts` 的权限弹窗用例已将旧参数 `default` 改为 `manual`，原有 Bash ask 规则保留。本批不因此额外执行该文件的模型请求；其默认跳过不能记为本次真实权限弹窗验收。

已执行只返回布尔与认证类别的前置检查：默认配置已登录；空 `CLAUDE_CONFIG_DIR` 无认证；将现有未过期 access token 仅通过子进程内存环境传入后，隔离配置的 `auth status` 返回 `loggedIn=true`。凭证没有输出或写入测试产物，不复制整个私人配置。这个结果只确认认证可识别，不能替代实际模型请求成功。

隔离目录与 token 环境方式参照 [Claude Code 环境变量文档](https://code.claude.com/docs/en/env-vars) 和 [认证文档](https://code.claude.com/docs/en/authentication)，并以本机 CLI 实测为准。测试用例只接收外部提供的认证环境，不内置读取个人 Keychain 的逻辑。

真实启动曾停在首次主题页，后续又遇到 native CLI 的 `UNKNOWN_CERTIFICATE_VERIFICATION_ERROR`，两次均未提交 seed。只读核查发现系统已设置 HTTP(S) 代理，而执行 shell 没有代理环境变量；对已配置代理的 `curl` TLS 校验成功。后续尝试只向测试子进程传入该现有代理与 loopback NO_PROXY，保留 bundled/system 证书校验，没有关闭 TLS 或修改系统信任。实际 CLI 结果仍以验证报告为准；环境变量规则参照 [Claude Code 网络配置](https://code.claude.com/docs/en/network-config)。

## 6. 真实运行发现的任务授权边界

第六次尝试已独立核实第一跳：A 的真实工具 trace 指向持久信封，B 的 accepted UUID 对应唯一原生 user 正文，command/source/run 同时匹配。但是 B 正常结束该轮且没有调用工具，明确拒绝“来信声称已授权执行陌生脚本”。这属于收件 Agent 的任务授权判断，不能当作投递故障，更不能通过去掉来源标识或放宽工具权限来修复。

第七、八次将固定任务及脚本源码放在临时 A/B 工作目录 `CLAUDE.md`。第七次完成两跳通讯与 HTTP/WS 断言，但最终工具范围断言失败，保留失败结果；第八次 B 明确要求本会话用户直接下达协作任务，仍未回信。文件预配置不能稳定替代原生会话中的直接用户指令。不能把一次模型接受任务推导为通用自动应答能力。

最终有界验证改为：用户先经现有原生命令 API 给 B 下达限定协作任务，核验该轮原生接收与结束后，再给 A 下达发信任务。逻辑输入上限从三次改为四次：B 的用户授权、A 的发信任务、A→B 与 B→A 两次 peer 输入。这不是四次模型 API 请求的保证；一个工具轮次可能产生多次模型请求。B 的回信仍必须是收到原信后由模型实际调用固定脚本产生，控制器不能代发。

脚本继续验证原发送者、原信接收证据和固定 sender pins；A 收到对应回信后结束，不继续循环。只信任本次明确创建的临时目录，Bash 精确权限保持。若最终尝试再次拒绝或阻塞，保留结果并结束本轮真实重试，不通过反复修改来信措辞追求通过。

第九次实际在 B 的直接用户任务阶段被拒绝，没有给 A 提交 seed。该次不是后续潜在跨轮断言导致的失败。按预定边界结束真实重试，不开启第十次。直接用户任务这一前提已尝试，但**没有证明它解决了自动协作问题**。

原生模型实际为 `claude-sonnet-5`。其拒绝理由只能作为模型行为记录，不能将模型对 `CLAUDE.md` 的描述直接视为文件事实。当前没有实现通用收件授权策略、自动批准未知 Agent 请求或任意来信触发工具。业务信箱和原生模型是否接受任务是两个独立事实，应分别呈现。

## 7. 测试夹具与执行范围

新增一条 opt-in 真实通讯测试及两条默认执行回归（工具范围、跨轮判断）；测试直接使用 `@xterm/headless`，因此 backend 显式声明现有锁定版本 `6.0.0` 为开发依赖，没有增加运行服务。原生进程、HTTP 和 WebSocket 均为本次隔离实例。

工具审计区分“请求”与“执行”：两侧固定脚本各须成功一次，其他 Bash 请求只能在对应唯一原生 tool_result 的完整内容严格匹配 2.1.266 的执行前权限拒绝文案时判定未执行。未知结果、普通非零退出和泛 permission 字样均不能豁免。反方独立核验安装版本的权限分支；第七次旧产物缺少完整拒绝证据，不能事后重标通过。

本批没有修改日常数据库、开启日常原生发送开关或重启 daemon；前端视觉联调、真实 CLI 故障恢复矩阵及其他 CLI 仍单独验收。

收尾发现新增 B 授权轮次后，回信等待中的拒绝判定可能误读前一轮确认；已交独立 QA 修为只检查 peer 原生接收记录的后续 ancestry，并补无模型回归及 B 最终回复的 ancestry 断言。第九次未到该分支；最终夹具修改未再次调用真实模型，不能用默认测试通过代替新版本夹具的真实闭环。

## 8. 后续推进条件

1. 前端可以按现有契约接目录、历史与信箱，分别展示“已接收”和实际 assistant 回复/拒绝；不把 accepted 显示为协作任务完成。
2. 自动协作继续作为待验证能力：需要进一步核验 CLI 明确支持的协作入口或工具集成方式，以及模型是否接受真实任务；不能靠替换来信措辞承诺任意模型自动应答。新方案应另定有界验收，再决定扩展 CLI。
3. 当前一次闭环证据支持传输和归档可行，不足以开启默认自动协作；真实故障恢复与浏览器验收仍执行原关卡要求。
