# claude 转录读取：风险实测与 SDK 到底能买到什么

2026-09-15。**纯调研，没有改任何代码。** 标 **[实测]** 的是本机跑出来的数字，
**[源]** 的是官方文档核到的。

起因：[terminal-flood/README.md](terminal-flood/README.md) 记过一条风险——我们直接解析
`~/.claude/projects/**/*.jsonl`，而官方称该格式内部、随版本变、**禁止自行解析**，正道是
Agent SDK 的 `getSessionMessages()`。这次是在动手之前把那条结论验一遍。

---

## 一、结论先说：**换 SDK 不能解决那条风险**

`getSessionMessages()` 的返回类型是 **[源]**：

```ts
interface SessionMessage {
  type: "user" | "assistant";
  uuid: string;
  session_id: string;
  message: unknown;   // ← Raw message payload from the transcript
  parent_tool_use_id?: string | null;
  parent_agent_id?: string | null;
}
```

**`message` 是 `unknown`，文档自己写着「原始 payload」。** 也就是说会漂移的那一坨原样递
回来，SDK 只替你做了「找文件」和「分行」。旧文档把 SDK 当成格式稳定性的解药，这一条
不成立——迁过去之后，解析 `message` 的活还是我们自己干，风险面一模一样。

另外两点也要记上 **[源]**：

- **没有游标分页**，只有 `limit` / `offset`。我们现在是按字节 checkpoint 增量追读一个
  正在增长的文件，换成 offset 分页意味着每次重扫。
- **对「正在被写入的会话」的行为文档没有定义。** 而「一边跑一边看」正是这个产品的核心用法。

## 二、风险到目前为止**没有发生过** [实测]

拿本机 40 份真实转录，带 checkpoint 读到底：

| 指标 | 数字 |
| --- | --- |
| 产出条目 | 6285 |
| 含「未支持内容」的条目 | **0** |
| 被截断的（字节预算所致，设计如此） | 1002 |
| 角色分布 | user 290 / assistant 4041 / tool 1954 |

转录里出现过的 claude 版本：2.1.269 / 2.1.270 / 2.1.271。**三个版本的记录 type 完全一致**
（`assistant, attachment, system, user`）。

**而且漂移是可检测的**：每条记录自带 `version` 字段。我们现在没用它——可以在认不出记录
形状时连同 version 一起记下来，而不是等用户发现历史缺了一块。

## 三、SDK 真正能买到的东西（和我们原以为的不同）

1. **找文件的正确性** **[源]**：工作目录编码成 `-` 分隔的目录名，**超过 200 字符会截断
   并追加 hash**；v2.1.223 起还支持跨目录查找。我们在 `discoverClaudeTranscript` 里自己
   实现了一份，没有这两条。
2. **会话元数据** **[源]**：`listSessions()` 给 `summary` / `customTitle` / `firstPrompt` /
   `gitBranch` / `cwd` / `tag` / `createdAt`。
3. **子代理归属** **[源]**：`parent_tool_use_id` / `parent_agent_id`。见下面第五节。

## 四、不用 SDK 就能拿到的：claude 自己的标题 [实测]

转录里有这种记录：

```json
{"type":"ai-title","aiTitle":"Orca 项目评估","sessionId":"65b59f76-6e56-4481-8bb6-bcff55fab160"}
```

对着本机真实对话核过：**4 条 claude 对话里 2 条有 `ai-title`**（omp 没有，那是另一套格式）。
其中 `orca_agent` 那条，目录里显示「Terminal」，claude 自己叫它「Orca 项目评估」。

这不需要 SDK——它只是我们已经在读的那个文件里的又一种记录类型。

注意这条和 [235ab6b] 的标题修复是**互补**而不是重复：那次是在没有真名字时退回显示第一条
用户消息，这条是拿到一个**真的名字**。

## 五、更大的一个发现：子代理的记录我们完全看不到 [实测]

`discoverClaudeTranscript` 只扫两层（root → 项目目录 → 文件）。而子代理的转录在
`<项目目录>/subagents/agent-<id>.jsonl`，**在第三层**，够不着。

这些文件的内部 `sessionId` 是**父会话**的 id——所以它们不是独立会话，是同一条对话的一部分。

| | 文件数 | 体积 |
| --- | --- | --- |
| 主会话转录 | 29 | 83 MB |
| **子代理转录** | **75** | **138 MB** |

也就是说本机转录字节里**约六成是子代理的内容，而目录里一条都没有**。对「让多个 agent
一起干」这种用法，看到的历史是残缺的。

（这个比例受最近用法影响很大，不要当成普遍规律；但「完全看不到」这件事与用量无关。）

## 六、建议的顺序

1. **不要为了「格式安全」去迁 SDK。** 它不提供那份安全，还会丢掉增量追读，并且在
   「正在写入的会话」上行为未定义。
2. **先做 `ai-title`**：便宜、无新依赖、直接改善目录可读性。认不出就不用，退回现有兜底。
3. **再看子代理**：这是覆盖率缺口，不是风险。要先想清楚子代理消息在界面上怎么归属
   （嵌在父回合里？还是折叠成一条？），否则会把 138 MB 内容平铺进对话里。
4. **补一个漂移探针**：记录认不出的记录形状 + 当时的 `version`。有了它，「格式变了」会
   变成一条可观测的事实，而不是一个悬着的担心。
5. SDK 留给两件它确实更强的事：**找文件的边界情况**（>200 字符截断、跨目录查找）和
   **子代理归属**。要接的时候按这两条的价值单独立项，不要打着「更安全」的旗号。
