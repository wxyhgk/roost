## 结论：先解决历史存储，再放开自动换绑

用户想要的是：终端切换对话后右侧跟着切、旧内容还能找回、长对话能向前翻、不同 CLI 都能接入。四个方向共享同一基础：**原生对话、终端绑定时期、传输游标必须分开**。

建议阶段：

| 阶段 | 交付 | 用户收益 | 完成门槛 |
| --- | --- | --- | --- |
| P0 | 耐久消息存储、读取检查点、历史分页及旧代索引 | 旧对话不再只存在有限缓存或 CLI 文件里 | 源文件删除后已入库正文仍可读；分页期间追加无重漏；断电模拟不提前提交 offset |
| P1 | 归档与新绑定同事务、安全自动跟随、跨代流更新 | `/new`、resume、A→B→A 可以继续用，不丢旧内容 | 来源证据不足不猜；旧代迟到帧隔离；并发切换仅一个成功 |
| P2 | omp 历史树、压缩摘要、分支可确认程度 | 能区分不同分支和压缩前后记录 | 不把文件末行无条件当 TUI 活动分支；明确标注推断/未知 |
| P3 | Claude 首个新适配器验证，再评估 OpenCode、Codex | 更多 CLI 有结构化对话视图 | 同项目两个 CLI 进程不串会话；退出/恢复/版本不支持能降级 |

P2 的字段预留和未知分支提示应在 P0 一起确定，避免先把树状记录固化成不可修正的平面“当前对话”。完整 P2 行为另交付。

## 统一模型约束

- `conversationId`：持久化原生对话身份；采用 provider/来源命名空间 + nativeSessionId，未来可加机器/配置作用域，不能用 cwd 或标题当唯一身份。
- `generation`：某网页终端绑定该对话的一段时期。A→B→A 是三段绑定时期，但 A 的正文不应复制两份。
- 消息/记录：保留原生稳定 ID、parentId、记录类型、来源、schema/adapter 版本和覆盖状态。相同 ID 的修订需要版本/hash，不应仅 `INSERT IGNORE` 后永远不更新。
- `historyCursor`：数据库分页位置，绑定会话与查询快照边界；与 `afterSeq`（WS 回放）、daemon sourceSeq、文件 byteOffset 分开。
- `projectionRevision`：当前展示集合/分支发生替换时区分旧视图与新视图；不通过篡改 nativeSessionId 表示文件换代。

具体 DDL 以 P0 实施前的统一规格为准，专题中的表名/API 示例是候选设计。优先复用 workspace-store 的 SQLite 连接和事务；无需新增服务、ORM 或自建消息队列。

## 已核对的当前缺口

1. `packages/workspace-store/src/ai-sessions.ts:6-18` 使用一行 `record_json` 保存整个 bridge 缓存，启动 `list()` 读取所有记录。扩大缓存不是分页方案。
2. `packages/ai-session-bridge/src/index.ts:84-95` 的 rebind 构建空 events 的新记录并删除旧订阅，没有历史归档。已有正文时应先解决归档再自动放行。
3. `backend/src/server.ts:165-181` 的手工 rebind 按来源日志寻找最后一个 ID，但没有检查 page.hasGap，也没有固定跨页 highWater。自动换绑不能直接照搬这个扫描器作为“当前身份已证明”。
4. `backend/src/ai-session-stream.ts:23-34` 的监控闭包捕获初始 snapshot.generation。原地跨代切换必须重建/更新订阅和监控；前端支持快照替换不代表后端已经支持同 socket 跨代。
5. `backend/src/server.ts:138-147` 的详情入口依赖当前可见缓存中的文件位置。源文件消失、改写或缓存淘汰时，不能保证详情仍可读。P0 必须明确保存哪些已解码正文/详情及其上限。
6. `packages/workspace-store/src/store.ts:54-61` 当前删除终端会依次清理来源日志、AI 记录、终端回放和终端行。新增归档后应把相关删除纳入事务，不能留下半删状态。

## 不应照搬的设计

- Happier 的逐条消息、来源适配、稳定 ID 值得借鉴；不需要同时引入它的远程账户、加密同步和完整执行器。
- Warp 可借鉴长期 session/conversation 身份、懒恢复和边界隔离；它拥有自己的终端/agent 状态，不能据此推断我们旁读任意 CLI 文件就能知道全部 TUI 状态。
- 不通过复制多份 8 MiB JSON 来长期归档；也不把 WS 热缓存扩成无限历史。
- transcript 暂时不可读时，应保留耐久历史并报告新鲜度。新 OSC 片段保留明确来源；没有原生对应 ID 时，不靠文本相似或时间接近强行去重。
- 旧记录迁移只能挽救目前仍保留的事件；曾被淘汰且源文件也不存在的正文无法凭空补回，应报告覆盖范围。

## 第一轮建议实施范围（P0）

1. 定稿 conversation / binding generation / message / source checkpoint 的最小表结构；沿用 CAS、唯一键和单连接事务。
2. 在同一提交中写入一批标准化记录及读取检查点，WS 仅在提交成功后通知。保留有限回放缓存。
3. 新增对话历史页、历史代列表和按消息 ID 取已存详情的接口；不改变原 snapshot/WS 契约。页面数量和响应字节双上限。
4. 对旧 JSON 记录做幂等迁移，记录迁移覆盖范围；明确失败恢复与版本回滚读取策略。不要让旧进程和新进程同时双写两套事实来源。
5. 测试大历史懒加载、重复读取/消息修订、跨页追加、事务失败、缓存淘汰、源文件消失、删除一致性。性能验收先测基线，再固定预算，不承诺未测过的毫秒值。

P1 再将「结束旧 generation + 建立新 generation + 更新当前绑定指针」做成事务，并把来源证据判定抽成可测试函数。第一版仍限制同一原生对话只有一个活动绑定；多终端同时操作同一原生会话另议。

## 前端交接边界

后端先交付接口及 fixture，前端只需按阶段接历史分页、代列表、来源/覆盖提示。跨代依然是新快照替换；翻阅历史不得改变活动终端或触发 CLI resume。权限批准、GUI 发送消息、自动注入按键不在本次范围。

所有专题结论属于源码/文档调研；没有把第三方项目运行结果或拟议接口当成已完成的集成测试。
