# 共享终端尺寸控制：多方向设计与反方审查

日期：2026-09-07。状态：完整仲裁方案暂缓；用户选择轻量修复，见下文。

## 后续决定：先做轻量修复

用户要求不必特别完美，因此本次不增加 daemon 所有权、令牌或接管按钮。下文完整设计留作参考，并非当前实现要求。

当前实现：

- 前端 ready 不再携带尺寸，业务网关也忽略旧客户端 ready 中的尺寸；握手只负责恢复输出。
- 回放解析完成后，只有当前选中、页面可见且窗口聚焦的终端发送显式 resize。
- 相同尺寸不重复发送；切回窗口或终端、重连回放完成时强制同步一次，避免旧缓存阻止恢复尺寸。
- 稳定工作台仍保留原来的主动交互限制，并增加窗口焦点检查。
- 本地渲染器仍随容器适配；是否修改共享 PTY 尺寸单独判断。

验证：前端 89 项测试、后端终端恢复 11 项测试通过。覆盖未就绪、未选中、后台/隐藏窗口、重新聚焦、尺寸去重，以及被动连接和旧 ready 不修改 PTY 尺寸。后端测试使用假 PTY，确认显式 resize 生效且连接前后 PID 不变；未操作用户正在运行的终端做多窗口验收。

边界：这不是跨设备互斥协议。不同设备同时聚焦、尚未刷新的旧页面、旧版已安装网关仍可能争抢尺寸。本次不重启 daemon、不覆盖已安装稳定产物；业务网关改动需重新加载服务后生效，新前端不携带 ready 尺寸则可兼容旧网关。

## 讨论背景

此前调查发现，多个浏览器或网关可以直接调整同一个 PTY 的尺寸。较窄页面被动连接、重连时，可能把正在使用的大窗口里的 CLI 改窄。截图与此机制相容，但缺少当时尺寸时序，不能把所有空白都归因于这一点。

本轮由五个 subagent 分别审查 daemon/协议、前端交互、兼容升级、测试验收，最后由反方 agent 交叉挑刺。均为只读调查，没有操作用户 PTY。

## 最终推荐：仅仲裁尺寸，不增加输入独占

每个 PTY 同一时刻只有一个客户端能修改尺寸。其他页面仍可连接、查看和按现有方式输入；本轮不承诺跨窗口同时输入时的尺寸与字符原子一致性。

UI 使用“在此控制尺寸”，避免“在此操作”让人误以为其他窗口不能输入。

### 交互规则

| 行为 | 是否获取尺寸控制权 |
|---|---|
| 打开旧会话、ready、回放完成、重连 | 否 |
| 窗口聚焦、显示标签页、切换会话 | 否 |
| 鼠标经过、滚动、选字、复制 | 否 |
| 点击“在此控制尺寸” | 是，携本地期望尺寸申请并等待确认 |
| 主动新建会话 | 可以在创建流程中显式申请；不能把所有 ready 都当作主动创建 |
| 当前控制窗口调整面板或窗口大小 | 发送经过权限校验的尺寸更新 |
| 非控制窗口调整自己的面板 | 不修改 PTY |
| 设备、焦点、颜色等协议回复 | 不申请 |

控制窗口暂时失焦不释放所有权；隐藏或非活动会话停止发尺寸。其他窗口随时可以通过明确动作接管，因此首版不需要 TTL、续租或自动竞选。

## 协议与仲裁

权威状态放 daemon，不能只放 8787 或 8788；否则两个网关仍会各自认为自己有权改尺寸。

每个 `(sessionId, instanceId)` 保存：控制者、递增代际、最后应用的 cols/rows。

- 控制者绑定真实 daemon IPC socket 与网关为浏览器 WS 创建的 attachmentId。
- 不使用名称、sessionId 或浏览器自报 windowId 作为唯一控制身份。
- ready 仅握手/回放，两个网关都取消其隐式 resize 副作用。
- claim 在 daemon 中顺序执行“转移控制者、递增代际、应用尺寸”，返回确认及实际尺寸。
- resize 必须匹配当前 socket、attachment、instance、代际；旧请求明确拒绝，不断开正常回放连接。
- 显式 release 若提供，也必须校验同样的身份和代际。首版释放触发点以 WS 断开、IPC 断开、会话结束为主。
- 网关 IPC 断开时清理其拥有的控制权；旧连接的延迟释放不能清掉新控制者。
- 无控制者时保留最后 PTY 尺寸，不自动改回 80×24，也不让旁观窗口自动补位。
- 相同尺寸可不重复执行 PTY resize；重新接管仍需完成确认，不能被客户端旧尺寸缓存跳过。

## 反方审查带来的修正

1. **“点击即接管”会误伤复制。** 现有 pointerdown/keydown 太宽泛；显式按钮比猜测用户意图可靠。IME、TUI 鼠标与拖选不必在首版同时重写。
2. **只等 claim ACK 不能保证下一字符的尺寸。** A 获确认后，B 仍可能先接管，A 再输入。若要强保证，需要输入代际校验/ACK/草稿保留，或 daemon 原子 activateAndWrite。本轮选择不做输入独占，明确保留共享输入语义。
3. **lease 心跳不是必需。** 显式接管可替换失联控制者，socket 断开可清理；增加 TTL 反而引入休眠和后台计时器问题。
4. **控制窗口正确，不等于旁观窗口精确镜像。** 当前各 xterm 根据自身容器 fit。首版允许旁观画面不完整并提示“尺寸由另一窗口控制”。权威网格、横向滚动/裁切、历史尺寸回放另行设计。
5. **旧 resize 入口不能留后门。** 新 daemon 若仍执行无身份的旧 resize，新保护就可被旧 core 绕过；这是上线阻断项。
6. **截图不是完整根因证明。** 必须对照容器宽度、本地 xterm 列数、daemon 已应用列数和真实 PTY 列数，排除 CLI 自限宽度与历史内容。

## 兼容与升级边界

现有浏览器协议严格解析未知消息；旧 daemon 的 notify 也可能吞掉未知操作。新增能力必须经握手确认，claim 必须有请求确认，不能盲发。

建议新增可选能力 `resizeOwnership: 1`，仅在当前网关和 daemon 都支持时向浏览器宣告。浏览器重连后不重放旧 claim/token。

| 组合 | 行为 |
|---|---|
| 新前端＋新网关＋新 daemon | 完整尺寸仲裁 |
| 新前端遇旧网关或旧 daemon | 不发送未协商消息，不声称有跨窗口保护 |
| 旧前端或旧网关遇新 daemon | 回放/输入保留；无控制身份的旧 resize 拒绝执行 |
| 新旧 8787/8788 混用 | daemon 仍统一拦截，不能依靠新网关局部保护 |

旧客户端保留全部 resize 行为与可靠尺寸保护不可兼得，应明确记录降级。已安装 core/stable 是独立产物，修改仓库不会更新它们。旧 daemon 换新代码不能承诺保留现存 PTY；需要等任务结束再安排升级。网关重启在同一新版 daemon 下应保留 PTY PID。

## 验收门槛

先扩展 FakePty，记录真实有序 resize/write 调用；目前空实现不能证明尺寸安全。

P0：

1. 宽窗口控制时，窄窗口被动连接、ready、回放、重连均不改尺寸。
2. 窄窗口显式接管后，旧控制者延迟 resize/release 被拒。
3. 并发 claim 得到唯一顺序，旧代际失效；无人控制时保留最后尺寸。
4. WS/IPC 断开、后台冻结恢复、PTY instance 替换均不能复用旧身份。
5. 去重不阻止重新接管同步；非法/零尺寸不进入 PTY。
6. 单一隔离 daemon 接业务和 core 两个网关，跨网关重复以上测试。
7. 新旧版本混用不通过 legacy resize 绕过保护；能力不支持时不发送新消息。
8. 输入仍按既有规则工作，不因为尺寸仲裁被默默丢弃或声称独占。

发布前用隔离真实 PTY 验证内核 rows/cols 与 PID 保留。WebSocket pong 不是 daemon 执行完毕的屏障，使用操作 ACK/权威状态断言。PTY resize 成功也不代表 CLI 已处理 SIGWINCH 并完成重绘。

诊断只记录有限条尺寸事件：时间、匿名连接标识、会话/instance、网关、代际、请求/应用尺寸、接受或拒绝原因；不记录输入输出正文、命令、路径或可复用控制 token。

## 实施顺序

先做 daemon 状态机与双网关测试，再接能力协商和前端按钮，最后验证混合版本并安排升级。输出冻结改为保留上一帧、hydrate 无效选中项以及多窗口精确镜像，保持为独立任务。
